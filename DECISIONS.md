# Design decisions

Key design decisions in agentguard, each with the reasoning and what it would cost if it turned out wrong, in the format
`<what> — <why> — <cost if wrong>`.

- Taint is tracked per conversation context, not per value — an LLM can copy, paraphrase or re-encode any token it has seen into any later argument, so value-level tracking would be unsound — if wrong (finer tracking were sound), we pay avoidable approval prompts; the evaluation reports that cost.
- The policy parser rejects `taint.high: allow` (globally and per task) — the "no high-impact action from a tainted context without a human" invariant should not be one YAML line away from being switched off — teams that truly want it must change code; the evaluation's ablation builds such a policy programmatically and is labelled as an ablation.
- Context taint keeps a 'medium: allow' default in the shipped policy — writing reports and notes after browsing is the main point of research/inbox tasks and the writes are contained and labelled — a tainted session can create arbitrary files inside its granted folders (visible in held-out `attack-organizer-env-copy`); tighten with `taint.medium: require_approval`.
- Own closed JSON-Schema subset instead of the `jsonschema` package — at a security boundary, unknown keywords must be errors, not silently ignored, and `additionalProperties` should default to false — less expressive schemas for tool authors.
- Grant constraints may only target *required* arguments (bind-time error otherwise) — an omitted optional argument would skip the constraint entirely — tool authors must make constrained arguments required.
- Added per-capability argument aliases (`ToolSpec.arg_aliases`) — an engine test with a `copy(path, dest)` tool showed fs.write grants were checking `path` (the source) and leaving the destination unconstrained — one more concept for tool authors.
- Glob compiler rewritten to emit `/seg` and `(?:/[^/]+)*` tokens over the rooted path — the hypothesis property test against a recursive reference matcher found consecutive `**` segments mis-compiled — none (stricter and simpler).
- Amounts are compared as exact `Decimal`s built from `repr(float)`; booleans are never numbers; NaN/Infinity fail closed — float rounding and `True == 1` are classic limit bypasses — slightly surprising behaviour for callers passing floats like 0.1+0.2.
- Rate limits and budgets are checked in `decide` but committed only after the handler ran — refused or denied calls must not burn quota, and `decide` stays pure/testable — a crash between execution and commit could under-count (in-process, single-threaded, so not observed).
- A tool that *errors* still counts against the tool-call cap and rate limit, but not the budget — the call was attempted (rate) but no money moved (budget) — an attacker can exhaust a rate window with failing calls (DoS only).
- `list_inbox` returns only validated structured headers (id, address, verified flag) and is labelled trusted — triaging must not taint the context, and subjects are attacker-controlled text — the model sees less information when choosing which mail to open.
- Monitor mode still refuses structurally broken calls (unknown tool, non-object or schema-invalid arguments) — handlers must never see unvalidated input — the unguarded baseline is slightly less than "no guard at all".
- Approval hooks fail closed (exceptions and non-`ApprovalResponse` returns are refusals) — an approval UI bug must never approve — a flaky UI blocks work.
- Audit records hash canonical JSON (sorted keys, ASCII, no whitespace); sensitive arguments are replaced by an unsalted SHA-256 prefix — stable hashing across serialisers; proves what was sent without storing it — low-entropy secrets can be brute-forced from the digest (documented).
- Truncation detection needs an out-of-band head anchor and whole-chain rewrite detection needs an HMAC key — a self-contained hash chain cannot detect either — deployments that skip both only get edit/reorder detection (documented in THREAT_MODEL).
- The fake model in attack scenarios obeys every injection — models the worst case so results measure the guard, not the model's gullibility — numbers are pessimistic about real models, which the llama3.1:8b run complements.
- Scenario outcomes are judged from world state, never from the model's final message — models misreport what they did — predicates are only as good as the fixture.
- Held-out scenarios were written after `policies/assistant.yaml` was committed and no policy change followed — evaluations must not tune and report on the same data — the held-out set is small (18 scenarios) and written by the same author, so it is not independent in any statistical sense.
- Kept `attack-organizer-env-copy` unchanged after it "succeeded" under the guard on the held-out split — its attack goal (file exists) was declared before the run; changing it afterwards would be tuning on held-out data — the headline shows 1/8 held-out attacks succeeding even though no credential was actually read (the scripted model wrote a token it was never given).
- `fetch_url` is an egress tool but low impact — browsing must stay usable after the first page; URL constraints carry the exfiltration defence — data can leak through *which* allow-listed URL is fetched.
- Stdlib `urllib` client for the OpenAI-compatible API instead of an SDK — one dependency fewer on the security path, tests inject a transport — fewer conveniences (no streaming).
- Small-model tool calls printed as JSON text are salvaged into real tool calls — otherwise llama3.1:8b turns would bypass mediation by never being executed at all, and the run would under-report what the model attempted — a false salvage still goes through the guard, so the risk is only a spurious call.
- The real-model run uses only `unguarded` and `guard-unattended` — the real model is the slow part (shared local Ollama); those two configs answer "does the model fall for the injections" and "what does the guard cost" — no real-model numbers for the rubber-stamp and ablation configs.
- Coverage gate at 85% (measured 99%) — contract requires ≥ 80% core coverage — none.
- Deny rules match list-valued arguments existentially (any element satisfying all of that argument's constraints fires the rule) while grants stay universal (every element must pass) — an earlier version let `{paths: ['a.txt', '.env']}` past a `**/.env` deny, because the deny only fired when *all* elements matched, so deny rules failed open — an empty list no longer triggers a deny rule (it has no forbidden element; grants still decide it), and a deny rule now fires on a list containing an invalid element only if that element itself satisfies the deny constraints.
